# Вход и сессии

Для входа нужны почта, существующий профиль и одноразовый код из письма. Клиентская форма запрашивает только почту; отдельный вход для сотрудников позволяет выбрать разработчика или администратора. Выбор роли не создаёт аккаунт. Подтверждение открывает только выбранный профиль. Доказательство входа в `auth_profile_verifications` связано с группой устройства, ID пользователя, ролью и сроком сессии; смена роли отзывает прежнее подтверждение. Код также привязан к запрошенной роли, указанной в письме.

Только администратор создаёт разработчиков: раздел «Разработчики» → «Создать разработчика», имя и почта. GET/POST `/api/portal/admin/staff` проверяют роль на сервере, POST также проверяет Origin и CSRF. Сервер задаёт роль `developer`, запрещает подмену на `admin`, сохраняет автора создания и идентификатор запроса. Повтор того же запроса не создаёт второй аккаунт или приглашение. Зашифрованное приглашение доставляется через очередь. Создание администраторов через HTTP отсутствует; первый администратор настраивается оператором. Несколько разработчиков поддерживаются базой: общая очередь содержит свободные и собственные проекты, проекты другого разработчика и их содержимое недоступны.

Добавление профиля означает вход в уже существующий аккаунт. Клиент может добавить только свою роль. Разработчик может войти в существующий профиль администратора после отдельного кода с его почты; до подтверждения права разработчика сохраняются. Администратор также может подтвердить дополнительные роли отдельными кодами, включая профили на той же почте. Подтверждённые профили переключаются через меню без выхода и повторного кода до конца исходной сессии. Подключение профиля не создаёт аккаунт и не меняет серверные ограничения на создание сотрудников. При одинаковой почте у нескольких ролей владелец этого ящика может самостоятельно войти в каждый уже выданный ему аккаунт через соответствующую форму. Для независимых людей нужны разные почтовые адреса.

До подтверждения кода нет авторизованной cookie, CSRF-токена или доступа к данным. Код действует 10 минут, используется один раз и привязан к отдельной HttpOnly cookie браузера. В SQLite хранится HMAC. После пяти неверных попыток подтверждение недействительно. Дополнительно ограничены запросы и проверки по почте и IP. Повтор доступен через минуту, меняет код и не обнуляет попытки.

Запросы для известной и неизвестной почты возвращают одинаковую структуру. Для неизвестной создаётся непригодное для входа подтверждение без аккаунта и без отправки письма. Автоматической регистрации нет. Письма с кодами попадают в зашифрованную durable-очередь: ошибки отправки видны администратору, повторы используют тот же ключ идемпотентности. Просроченные, отменённые и заменённые коды не отправляются.

Веб-сессия и Mini App в обычном браузере действуют 12 часов с момента входа. Новый подтверждённый вход внутри Telegram действует до 30 дней. Серверный срок и Max-Age cookie согласованы; опрос данных, восстановление и переключение профилей не продлевают срок. Существующие сессии сохраняют прежний срок до следующего входа по коду. После истечения серверной сессии и после выхода нужен новый код.

На клиентах Telegram 9.0+ gateway сохраняет действующий токен и срок в [SecureStorage](https://core.telegram.org/bots/webapps#securestorage), отдельно для Telegram-профиля. Если WebView при закрытии потерял cookie, следующий запуск передаёт токен через `X-Portal-Session` вместе с новым подписанным `initData`; сервер повторно проверяет сессию, роль, подтверждения и контекст и восстанавливает HttpOnly cookie без продления срока. Заголовок принимается только в подписанном Telegram-контексте при `X-Portal-Secure-Storage: 1`. В браузерном контексте и другом Telegram-профиле токен не действует. Изменяющие запросы сохраняют проверку Origin и CSRF.

Токен возвращается в `nativeSession` только в ответах входа, переключения и чтения сессии/снимка, явно запросивших SecureStorage. Gateway удаляет транспортное поле до передачи данных интерфейсу. Данные авторизации не попадают в localStorage, sessionStorage, URL или очередь ошибок. При недоступном SecureStorage остаётся вход через cookie. Выход очищает защищённое хранилище и отзывает серверную группу. Завершение всех сеансов отзывает также сохранённые токены остальных устройств; после следующей проверки они удаляются локально. Обновления Docker сохраняют базу и не сбрасывают вход.

HTTPS использует HttpOnly, Secure, SameSite=Lax и host-only cookie с префиксом `__Host-`. Mini App использует отдельные HttpOnly/Secure/SameSite=None/Partitioned cookie для каждого Telegram-профиля. Сервер проверяет HMAC подписанного `initData`, срок запуска до 12 часов и числовой ID. Группа сессии и подтверждение почты привязаны к этому контексту; подмена имени cookie не переносит доступ. Подписанный запуск не заменяет код из письма и не назначает роль. `initDataUnsafe`, username и параметры URL не аутентифицируют пользователя. Для открытия Mini App в обычном браузере выделен отдельный контекст. Запросы изменения данных проверяют Origin и CSRF; добавление другой почты привязано к текущей группе и родительской сессии.

После обновления общие старые cookie Mini App больше не читаются: каждому Telegram-профилю нужно один раз заново войти по коду. Веб-сессии сохраняются. При переключении Telegram-профиля интерфейс сбрасывает кабинет, код, формы и уведомления, а поздние ответы прежнего контекста не применяются. Возвращение к профилю восстанавливает его собственную сессию до исходного срока. Выход действует на текущую группу, а явное завершение всех сеансов остаётся глобальным для почты.

После подтверждённого входа приходит уведомление с временем, профилем, IP и устройством. Ссылка «Это были не вы?» действует 24 часа и открывает `/recover/#token`. Открытие ничего не меняет. Подтверждённый POST завершает все связанные сеансы, отзывает коды и ссылки всех профилей на почте; повторное использование токена невозможно. Вход после этого требует нового кода. В настройках аккаунта доступно такое же действие с подтверждением и CSRF. Если злоумышленник имеет доступ к почте, необходимо защитить сам почтовый аккаунт.

HTTP-маршруты смены и восстановления пароля отключены с кодом 410. Старые внутренние поля credential сохранены для совместимости базы и версии отзыва; они не позволяют войти через HTTP. Новые приглашения клиентам содержат почту и инструкцию по коду. Старые задания отправки приглашений также формируют текст без временного пароля.

При первом обновлении с автоматического объединения ролей миграция завершает старые группы с несколькими ролями и связанные незавершённые подтверждения. Для них нужен повторный вход. Безопасные действующие сессии одной роли сохраняются и получают подтверждение профиля. Пользователи, проекты, переписка и платежи сохраняются. Миграция выполняется один раз; дальнейшие обновления сохраняют явно подтверждённые группы. Тесты: `tests/staff-accounts.test.mjs`, `tests/email-auth.test.mjs`, `tests/profiles.test.mjs`, `tests/miniapp.test.mjs`, браузерные сценарии входа, профилей, уведомлений и контейнера.
