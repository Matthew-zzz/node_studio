# Проект с несколькими репозиториями

Один клиентский проект может объединять до восьми GitHub-репозиториев. Например, AnimeLove содержит Frontend и Backend. Это связи в кабинете студии: каждый репозиторий сохраняет собственный код, задачи и историю GitHub.

## Создание и подключение

Новые проекты создаёт разработчик без GitHub. Разработчик изучает ТЗ в очереди, принимает проект и в обзоре нажимает «Создать GitHub-репозиторий». Создаются приватный основной репозиторий и первая Issue с ТЗ. Идентификатор репозитория резервируется для проекта до обращения к GitHub; повтор после сбоя не создаёт новый источник. Только назначенный разработчик может запустить эту операцию. Незавершённую резервацию нельзя присвоить другому клиентскому проекту.

Кнопка сохраняет фоновую задачу в SQLite и сразу возвращает управление. Создание продолжается после закрытия страницы и перезапуска контейнера. При сбое выполняется до восьми попыток с увеличением паузы; повторные нажатия не сбрасывают паузу и счётчик. В обзоре разработчик видит ожидание, выполнение, автоматический повтор или остановку. После восьмой неудачи доступна кнопка «Повторить создание»: она использует прежнюю резервацию. Ошибки записываются в журнал администратора с проектом и разработчиком, запустившим создание. Клиенту и разработчику техническое состояние создания не передаётся.

Откройте «Проекты и оплаты» → «Создать проект» → «Создать проект из репозиториев». Укажите название, почту существующего клиента, описание и репозитории в формате `owner/repository` либо URL GitHub. Первый источник становится основным. Перед сохранением сервер проверяет владельца, доступ и включённые Issues. Один репозиторий нельзя подключить дважды или отдать в разные клиентские проекты.

Созданный проект сразу назначается разработчику и появляется у клиента в существующем кабинете. Клиентский аккаунт не создаётся, письма и платежи не отправляются. Подключение уже существующих репозиториев — отдельная операция от создания нового оплаченного проекта разработчиком. У импортированного проекта нет отметки об оплаченной основной разработке.

В обзоре принятого проекта есть блок «Подготовить разработку». Каждый репозиторий показан отдельным подпроектом с собственным названием. У первого подпроекта можно задать имя и выбрать существующий репозиторий по GitHub-ссылке или создание нового. После подключения первого доступны дополнительные подпроекты с тем же выбором. Название подпроекта можно изменить; это не переименовывает репозиторий в GitHub. Клиенты, администраторы и разработчики чужих проектов не могут выполнять эти действия. Смена временного пароля и CSRF проверяются сервером.

## Отображение

Клиент видит один проект, общие этапы, задачи, объединённую историю коммитов и один чат. Названия и адреса внутренних репозиториев исключаются из клиентского объекта проекта на сервере. Другие клиентские проекты остаются недоступны.

Разработчик видит подпроекты в боковом меню. Внутри каждого доступны обзор, задачи и история; селектор «Область» переключает один подпроект или весь проект. При работе с двумя разделами оба используют выбранную область, а чат остаётся общим. Переключение подпроекта сохраняет черновик открытого чата. Для нового этапа можно выбрать репозиторий.

ИИ выделяет и уточняет пожелания в карточках согласования. После одобрения клиента задача создаётся в выбранном подпроекте; старые черновики используют первый, основной репозиторий. Изменения и отмена согласованных пожеланий требуют нового решения клиента. [Полный процесс задач](tasks.md). Рабочие задачи, этапы и коммиты загружаются из GitHub, предложения и история решений хранятся в SQLite. Номера задач уникальны внутри репозитория: подпроект входит в ключ записи, оценки и проверки оплаты. Поэтому `#1` во Frontend и `#1` в Backend не смешиваются. В клиентском списке технические номера GitHub не показываются.

Каждый источник имеет собственный кэш, состояние загрузки истории и паузу после ошибки. Сбой одного источника сохраняет его предыдущие данные и позволяет обновить остальные. Администратор получает отдельные записи с названием подпроекта. Webhook любого подключённого репозитория обновляет соответствующий источник. Обычные проекты с одним репозиторием продолжают работать; прежние ID задач и оплаченные оценки сохраняются при добавлении подпроекта.

## Операторский импорт

На сервере доступна команда `node server/cli.ts import-project`, принимающая JSON через stdin. Поля: `requestId` (UUID для повторов), `developerEmail`, `clientEmail`, `name`, `description`, `repositories: [{name, repo}]`. Используются существующие аккаунты и те же проверки, что в интерфейсе. После создания загружаются задачи и коммиты. Повтор с тем же UUID не создаёт второй проект или чат. Команда не сбрасывает работающие фоновые задачи приложения.

Данные связей и кэша хранятся в существующем томе `portal-data` и сохраняются при обновлении Docker. Токен GitHub остаётся в серверной конфигурации.

## Создание новых репозиториев подпроектов

Для нового подпроекта укажите название, выберите «Создать новый» и, при
необходимости, задайте имя GitHub-репозитория. Без имени репозитория сервер
выберет уникальное автоматически. Создание выполняется в фоне; в карточке
подпроекта видны очередь, повторная попытка или остановка после ошибки.
Незавершённый подпроект учитывается в лимите восьми, но не участвует в
синхронизации задач и истории.

Каждый подпроект имеет собственную сохранённую заявку, имя, маркер владения
GitHub и фоновую задачу. Повтор клика, потерянный ответ и перезапуск сервиса
продолжают исходную заявку. После восьми неудачных попыток доступна кнопка
«Повторить создание подпроекта». Имя GitHub фиксируется при запуске;
отображаемое название подпроекта можно менять независимо.

Первый источник сохраняет ID `main` и прежние ключи заявок и задач. Дополнительные
источники получают отдельные ID; одинаковые номера Issues не смешиваются.
Переименование не меняет репозитории, задачи, оплаты и общую переписку.
Подключение существующего репозитория не создаёт в нём задач или коммитов.

Проверки: `node tests/subproject-setup.test.mjs` покрывает создание и подключение,
переименование, независимые повторы после открытия SQLite, дубликаты, лимит,
права и CSRF. `node tests/repository-connection-browser.mjs` проверяет интерфейс
в веб-кабинете и Mini App на узком и широком экранах. Все проверки используют
изолированные GitHub-адаптеры; реальные репозитории не создаются.
