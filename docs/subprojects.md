# Проект с несколькими репозиториями

Один клиентский проект может объединять до восьми GitHub-репозиториев. Например, AnimeLove содержит Frontend и Backend. Это связи в кабинете студии: каждый репозиторий сохраняет собственный код, задачи и историю GitHub.

## Создание и подключение

Новые проекты создаёт куратор без GitHub. Разработчик изучает ТЗ в очереди, принимает проект и в обзоре нажимает «Создать GitHub-репозиторий». Создаются приватный основной репозиторий и первая Issue с ТЗ. Идентификатор репозитория резервируется для проекта до обращения к GitHub; повтор после сбоя не создаёт новый источник. Только назначенный разработчик может запустить эту операцию. Незавершённую резервацию нельзя присвоить другому клиентскому проекту.

В общей очереди разработчика раскройте «Создать проект из репозиториев». Укажите название, почту существующего клиента, описание и репозитории в формате `owner/repository` либо URL GitHub. Первый источник становится основным. Перед сохранением сервер проверяет владельца, доступ и включённые Issues. Один репозиторий нельзя подключить дважды или отдать в разные клиентские проекты.

Созданный проект сразу назначается разработчику и появляется у клиента в существующем кабинете. Клиентский аккаунт не создаётся, письма и платежи не отправляются. Подключение уже существующих репозиториев — отдельная операция от создания нового оплаченного проекта куратором. У импортированного проекта нет отметки об оплаченной основной разработке.

В обзоре проекта разработчик может раскрыть «Управление подпроектами» и подключить ещё один существующий репозиторий. Для этого проект должен быть взят в работу. Клиенты, кураторы и администраторы не могут выполнять эти действия. Смена временного пароля и CSRF проверяются сервером.

## Отображение

Клиент видит один проект, общие этапы, задачи, объединённую историю коммитов и один чат. Названия и адреса внутренних репозиториев исключаются из клиентского объекта проекта на сервере. Другие клиентские проекты остаются недоступны.

Разработчик видит подпроекты в боковом меню. Внутри каждого доступны обзор, задачи и история; селектор «Область» переключает один подпроект или весь проект. При работе с двумя разделами оба используют выбранную область, а чат остаётся общим. Переключение подпроекта сохраняет черновик открытого чата. Для нового этапа можно выбрать репозиторий.

Подтверждённые пожелания из общего чата создаются в первом, основном репозитории. Задачи, этапы и коммиты продолжают загружаться только из GitHub. Номера задач уникальны внутри репозитория: подпроект входит в ключ записи, оценки и проверки оплаты. Поэтому `#1` во Frontend и `#1` в Backend не смешиваются. В клиентском списке технические номера GitHub не показываются.

Каждый источник имеет собственный кэш, состояние загрузки истории и паузу после ошибки. Сбой одного источника сохраняет его предыдущие данные и позволяет обновить остальные. Администратор получает отдельные записи с названием подпроекта. Webhook любого подключённого репозитория обновляет соответствующий источник. Обычные проекты с одним репозиторием продолжают работать; прежние ID задач и оплаченные оценки сохраняются при добавлении подпроекта.

## Операторский импорт

На сервере доступна команда `node server/cli.ts import-project`, принимающая JSON через stdin. Поля: `requestId` (UUID для повторов), `developerEmail`, `clientEmail`, `name`, `description`, `repositories: [{name, repo}]`. Используются существующие аккаунты и те же проверки, что в интерфейсе. После создания загружаются задачи и коммиты. Повтор с тем же UUID не создаёт второй проект или чат. Команда не сбрасывает работающие фоновые задачи приложения.

Данные связей и кэша хранятся в существующем томе `portal-data` и сохраняются при обновлении Docker. Токен GitHub остаётся в серверной конфигурации.
