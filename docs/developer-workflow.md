# Единый кабинет разработчика

Активные роли: `client`, `developer`, `admin`. Разработчик получает Telegram-диалоги, подключение к человеку, генерацию и привязку брифов, создание проектов, ссылки на оплату и выдачу клиентского доступа. Управление ИИ и журнал ошибок остаются у администратора. Клиентская изоляция и ограничения доступа к репозиториям сохраняются.

В веб-кабинете глобальное меню разработчика содержит «Диалоги», «Общая очередь», «Проекты и оплаты», «Настройки». Внутри принятых проектов остаются обзор, задачи, история и чат. В Mini App первый экран — список диалогов; глобальная нижняя навигация переключается на разделы проекта при его открытии. Принятые проекты доступны через «Ещё» → «Мои проекты».

В форме «Создать для существующего клиента» есть выбор репозитория: «Создать новый» или «Подключить существующий». Для нового можно указать «Название GitHub-репозитория», например `AnimeLove-frontend`. Поле необязательное: без него сохраняется автоматическое имя. Допускается до 100 символов: латинские буквы, цифры, `.`, `_` и `-`; первый символ — буква или цифра, окончание `.git` не принимается. Вводится только имя без владельца и ссылки. Название сохраняется вместе с проектом и не передаётся клиенту. Выбор нового репозитория при создании проекта не требует подключения GitHub.

Для существующего вставьте `владелец/репозиторий` или HTTPS-ссылку GitHub, допускается окончание `.git`. Репозиторий должен принадлежать подключённому аккаунту, разрешать запись и иметь включённые Issues. Проверка выполняется до сохранения проекта. Повтор запроса не дублирует проект или чат. Созданный проект остаётся в общей очереди до принятия разработчиком; задачи и история загружаются из существующего GitHub. Новые репозитории, Issues и коммиты при подключении не создаются. Клиент получает единый проект без ссылок на GitHub.

В блоке «Подготовить разработку» у принятого проекта каждый репозиторий оформлен как именованный подпроект. У первого и дополнительных подпроектов можно подключить существующий репозиторий или создать новый, а отображаемое название изменить отдельно. Подключение существующего проверяет роль, назначенного разработчика, CSRF, активность проекта и уникальность привязки. Если создание нового репозитория уже запускалось, смена на существующий блокируется, чтобы фоновая задача не связала другой источник. Перед подключением после ответа GitHub эти условия проверяются повторно.

После принятия проекта поле также доступно в блоке подготовки разработки, в том числе для проектов, созданных после оплаты. До запуска можно изменить имя. Первая заявка фиксирует владельца, имя и идентификатор проекта; фоновые повторы и перезапуски используют ту же заявку. После запуска имя не меняется, чтобы потерянный ответ GitHub не привёл к созданию второго репозитория. Имена сравниваются без учёта регистра и резервируются между проектами. Созданный репозиторий содержит в описании маркер проекта; при повторе подключение разрешается только при совпадении маркера. Репозитории, созданные до этого изменения, продолжают восстанавливаться по прежним сохранённым заявкам. Посторонний существующий репозиторий не изменяется и не подключается автоматически.

## Обновление существующей установки

Перед обновлением сохраните резервную копию SQLite. `initializeAuthSchema` определяет старую схему и выполняет миграцию `server/developer-workflow-migration.ts` в одной транзакции с проверкой внешних ключей.

- Существующие клиент, разработчик и администратор сохраняют ID, почту, хеш пароля и действующие сессии.
- Прежний профиль сопровождения исключается из активных аккаунтов. Его сеансы, ожидающие коды и ссылки восстановления удаляются. В `retired_accounts` остаются только ID, почта, имя, прежняя роль и дата отключения; паролей там нет.
- Открытые им диалоги передаются существующему разработчику. Увеличивается ревизия диалога, чтобы устаревший ответ ИИ не мог вмешаться в работу человека.
- `curatorId` у проектов и связей брифов преобразуется в `createdBy`; источник старых проектов становится `developer`. Инициаторы незавершённых брифов и фоновых заданий передаются разработчику без сброса контрольных точек и попыток.
- История сообщений, авторы, исходные роли и временные метки остаются без изменений. Прежние записи ошибок также сохраняются; историческая роль не даёт права входа.
- В действующих промптах меняется упоминание роли на разработчика, остальные настройки сохраняются. Предыдущие настройки остаются в истории; восстановление старой версии нормализует название роли.
- Если в старой установке был только профиль сопровождения, он становится разработчиком с сохранением своих реквизитов. Повторный запуск миграцию не повторяет.

Новая установка создаёт два служебных аккаунта: разработчик и администратор. Клиенты получают доступ через обычный процесс проекта. Настройка владельца создаёт по одному аккаунту трёх активных ролей. Старый файл первоначального доступа не восстанавливает отключённый профиль.

Проверки миграции и прав: `node tests/developer-workflow.test.mjs`; весь набор — `npm test`. Тесты не отправляют реальные сообщения и не создают репозитории GitHub.
