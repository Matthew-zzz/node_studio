# Автоматическая публикация node-studio.ru

## Как обновляется сайт

```text
push в main
    ↓
GitHub Actions: lint → TypeScript → сборка → HTML + deployment tests → Chromium
    ↓ только при успехе
проверенный dist публикуется в ветку production
    ↓ системный таймер сервера, интервал 30 секунд
загрузка → проверка файлов → атомарное переключение current → проверка Nginx
    ↓ при ошибке
возврат к предыдущему current
```

Обычное обновление занимает время CI плюс до 30 секунд ожидания таймера и время загрузки релиза. Ошибка проверки оставляет предыдущий сайт. Pull request выполняет проверки без публикации. Не изменяйте `production` вручную: это результат сборки, исходники хранятся в `main`. Для репозитория с этим именем публичность обязательна: сервер получает готовую статику по HTTPS без токена. Приватный репозиторий потребует отдельной настройки доступа.

Next.js и Node.js на production-сервере не запускаются. Nginx обслуживает HTML и ресурсы. GitHub Actions использует встроенный `GITHUB_TOKEN` с `contents: write` только в задании публикации; SSH-ключи и GitHub Secrets этому способу не нужны. [Документация GITHUB_TOKEN](https://docs.github.com/en/actions/concepts/security/github_token).

## Однократная установка на существующем сервере

Поддерживается Debian/Ubuntu с Nginx и systemd. Нужны Python 3.12+, Git, curl, Certbot, flock и root для настройки службы. DNS-запись `A @` домена `node-studio.ru` должна указывать на `144.31.215.204`. Посторонние A/AAAA-записи необходимо исправить; порты 80 и 443 должны быть доступны. Установка проверяет DNS до внесения изменений.

1. Дождитесь успешных заданий `check` и `publish` в [GitHub Actions](https://github.com/Matthew-zzz/node_studio/actions/workflows/ci.yml). В репозитории появится ветка `production`.
2. В обычном терминале сервера, от root, выполните:

   ```bash
   cd /root/Work/node_studio/frontend/site
   git pull --ff-only origin main
   bash scripts/deploy/install-autodeploy.sh
   ```

   Это существующий путь проекта на сервере. Для другой копии репозитория используйте её каталог. Команду нужно выполнять вне ограниченной сессии Codex: ей необходима запись в `/etc`, `/usr/local`, `/var/www` и управление systemd.

3. Проверьте результат:

   ```bash
   systemctl status node-studio-deploy.timer --no-pager
   journalctl -u node-studio-deploy.service -n 30 --no-pager
   curl --fail https://node-studio.ru/deployment.json
   ```

`source_sha` в `deployment.json` должен совпасть с опубликованным коммитом `main`. Установщик также проверяет ответ публичного домена. Повторный запуск поддерживается: учётная запись и каталоги сохраняются, конфигурация обновляется. Файл `scripts/deploy-node-studio.sh` теперь вызывает этот же установщик.

Режим `--http-only` позволяет установить автообновления до настройки DNS/HTTPS. Он не подтверждает доступность сайта в интернете. После исправления DNS повторите обычный запуск для выпуска сертификата и включения HTTPS. Если Certbot завершился ошибкой, рабочая HTTP-конфигурация и уже включённый таймер сохраняются; исправьте DNS/доступность порта 80 и повторите установку.

## Что устанавливается

| Путь / служба | Назначение |
| --- | --- |
| `/usr/local/lib/node-studio/deployment.py` | Установленная root копия механизма обновления |
| `node-studio-deploy.service` | Однократное обновление под отдельным системным пользователем |
| `node-studio-deploy.timer` | Запуск после загрузки и через 30 секунд после завершения предыдущего |
| `/var/lib/node-studio-deploy/repository.git` | Кэш готовых статических релизов |
| `/var/www/node-studio.ru/releases/<commit>` | Проверенные релизы |
| `/var/www/node-studio.ru/current` | Ссылка на активный релиз |
| `/var/www/node-studio.ru/shared/_next/static` | Ресурсы текущих и прежних сборок для открытых вкладок |
| `/etc/nginx/sites-available/node-studio.ru` | Конфигурация этого домена |
| `/etc/letsencrypt/renewal-hooks/deploy/node-studio-nginx` | Перезагрузка Nginx после продления сертификата |

Служба ограничена отдельным пользователем и записью только в каталоги своего сайта и кэша. Содержимое `production` никогда не исполняется на сервере. Обновление самого установщика/службы требует повторного запуска установщика от root из проверенного `main`. Другие сайты не перенастраиваются.

`current` переключается атомарно, без остановки Nginx. Сразу после переключения проверяются байты главной страницы, трёх кейсов, robots, sitemap и deployment.json через настоящий virtual host на localhost. При HTTPS проверяется сертификат. Ошибка возвращает прежний `current`; неудачный релиз можно повторить, исправив причину. Сохраняются пять новых управляемых релизов, текущий и предыдущий. Каталоги старого ручного размещения не удаляются.

HTML и данные маршрутов требуют перепроверки кэша. Ресурсы `_next/static` имеют неизменяемые URL и годовой кэш; прежние файлы хранятся в `shared`, чтобы открытая вкладка могла дозагрузить JS после обновления. Этот каталог автоматически не очищается: следите за диском и очищайте старые ресурсы только при отдельном обслуживании.

Сертификат выпускается Certbot через webroot, автоматическое продление выполняет `certbot.timer`. Контактный email не задан; его можно добавить командой `certbot update_account --email your-address@example.com`.

## Диагностика и откат

Если сборка не появилась, сначала откройте GitHub Actions: задание `publish` запускается только после всех проверок. Его шаг `Report production DNS` показывает состояние публичного DNS и не блокирует сохранение готовой сборки.

Если `production` обновился, а сайт нет:

```bash
systemctl status node-studio-deploy.timer --no-pager
systemctl start node-studio-deploy.service
journalctl -u node-studio-deploy.service -n 50 --no-pager
nginx -t
curl --fail --resolve node-studio.ru:443:127.0.0.1 https://node-studio.ru/deployment.json
```

Проверьте исходящий HTTPS сервера к GitHub, права на каталоги сайта, DNS, сертификат и конфигурацию Nginx. Если установщик не нашёл `production`, дождитесь первого успешного `publish` и запустите установщик снова. При ошибке Nginx установщик восстанавливает прежнюю конфигурацию. Ошибки рабочей службы доступны в журнале systemd; проверка обновлений повторяется таймером.

Для возврата версии исходников используйте `git revert` в `main`: откат проходит тот же pipeline. Для срочного ручного переключения сначала остановите автообновления, иначе таймер снова активирует последнюю сборку:

```bash
systemctl stop node-studio-deploy.timer node-studio-deploy.service
ls -lt /var/www/node-studio.ru/releases
# Подставьте существующее имя проверенного релиза из вывода выше:
ln -s /var/www/node-studio.ru/releases/RELEASE /var/www/node-studio.ru/.manual-current
mv -Tf /var/www/node-studio.ru/.manual-current /var/www/node-studio.ru/current
```

После исправления исходников и успешного CI включите таймер: `systemctl start node-studio-deploy.timer`.

## Проверка механизма разработки

```bash
npm run test:deploy
```

Тесты используют временные локальные Git-репозитории: публикация не меняет исходную ветку/index, новый релиз продолжает историю `production`, устаревший workflow пропускается, повторное обновление не переключает сайт, ошибка health check возвращает прежнюю версию, старые ресурсы сохраняются, небезопасные архивы/ссылки/изменённые файлы отвергаются. Сетевые запросы и root тестам не нужны.
