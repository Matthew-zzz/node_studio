# Размещение через Docker

Приложение состоит из одного контейнера `app`. Многоэтапный Dockerfile собирает Next.js, затем копирует экспорт и сервер в runtime Node.js 24. Установленные зависимости фронтенда в runtime не попадают. Node.js обслуживает сайт и API на одном порту; контейнер работает под пользователем `node`, с файловой системой только для чтения и отдельным томом данных.

## Запуск

Из актуального checkout:

```bash
cp .env.example .env
docker compose up -d --build --wait
```

Стандартный адрес для существующего доменного proxy — `127.0.0.1:3158`. `PORTAL_ORIGIN` должен совпадать с адресом в браузере: для домена — `https://node-studio.ru`, для локальной проверки — `http://localhost:3158`. Ключи интеграций остаются в `.env`, исключённом из Git и контекста Docker-сборки. Для старта сайта и входа сотрудников внешние ключи не нужны.

Первый запуск создаёт сотрудников и секреты внутри постоянного тома. Доступы находятся в `/data/initial-access.json`, секреты — `/data/runtime-secrets.json`; права файлов 0600. Пароли не выводятся в журналы. При наличии сотрудников в существующей базе новые доступы автоматически не создаются.

## Подключение существующего HTTPS-домена

Сертификат домена остаётся у текущего Nginx. Контейнер не занимает порты 80/443. Сначала убедитесь, что `docker compose ps` показывает `healthy`, затем один раз подключите готовый proxy вместо прежней конфигурации статики:

```bash
cp /etc/nginx/sites-available/node-studio.ru /etc/nginx/sites-available/node-studio.ru.before-docker
cp deploy/nginx.conf /etc/nginx/sites-available/node-studio.ru
nginx -t
systemctl reload nginx
```

Если проверка Nginx не проходит, восстановите сохранённую конфигурацию. Шаблон использует существующий сертификат `/etc/letsencrypt/live/node-studio.ru/` и сохраняет webroot ACME для его продления. Остальные виртуальные хосты не изменяются.

Прежние таймеры публикации больше не нужны. После успешного переключения домена их можно остановить:

```bash
systemctl disable --now node-studio-deploy.timer
systemctl stop node-studio-deploy.service
```

Если отдельная служба API была установлена ранее, остановите `node-studio-portal.service` перед запуском контейнера: она могла занимать тот же порт 3158. Исходники старых установщиков и отдельного supervisor удалены из репозитория.

## Изменения и обновления

Рабочий порядок: внести изменение, выполнить проверки, отправить commit в `main`, дождаться успешного GitHub Actions, пересобрать контейнер. На сервере:

```bash
git pull --ff-only
SOURCE_REVISION="$(git rev-parse HEAD)" docker compose up -d --build --wait
docker compose ps
curl --fail https://node-studio.ru/api/portal/health
```

Ответ health содержит `revision`, заданный при сборке. Compose заменяет контейнер, сохраняя именованный том `portal-data`. Во время замены одного контейнера возможно краткое прерывание запросов. Провал проверки не является автоматическим откатом: повторно соберите исправленный или предыдущий коммит.

GitHub Actions проверяет приложение и Docker-образ, но не подключается к серверу: автоматический SSH-деплой и системные таймеры в новой схеме не используются. Обновление сервера выполняется прямой командой Docker Compose после push.

## Данные и настройки

- `/data/portal.sqlite` вместе с SQLite WAL — аккаунты, сессии, переписка, тестовые платежи и очередь.
- `/data/runtime-secrets.json` — постоянный ключ шифрования и начальные секреты webhook.
- `/data/initial-access.json` — почта и роли сотрудников первого запуска. В новых установках паролей нет; вход выполняется по коду на реальную почту. Старые файлы могут содержать неиспользуемые HTTP-входом пароли; храните их приватно.
- `.env` — origin, внешние интеграции и параметры Compose.

При резервном копировании сохраняйте весь том согласованно: остановите приложение либо используйте SQLite backup. Сохраняйте секреты вместе с базой; ключ нужен для недоставленных зашифрованных писем. Обычный `up --build` не удаляет данные. Удаление volume — отдельное разрушительное действие, не часть обновления.

Для переноса ранее созданной базы в новый пустой том сначала остановите API, перенесите согласованный SQLite/WAL и исходный ключ шифрования. Не заменяйте существующую базу пустой автоматически. В текущей установке отдельная API-служба ещё не была активирована; проверяйте состояние конкретного сервера перед миграцией.

## Диагностика

```bash
docker compose ps
docker compose logs --tail 100 app
docker compose exec app node server/healthcheck.ts
```

Для независимых установок используйте отдельное имя Compose-проекта. Порт настраивается `HTTP_PORT`, адрес привязки — `BIND_ADDRESS`; стандартная привязка только к loopback. `PORTAL_TRUST_PROXY=true` рассчитан на Nginx, который перезаписывает `X-Real-IP`. При прямом публичном доступе к контейнеру отключите доверие к этому заголовку.

В управляемой среде сборка может требовать proxy CA: Dockerfile поддерживает BuildKit secret `proxy_ca`. Используйте настроенный proxy и CA, не отключая TLS-проверку. Если Docker API возвращает `permission denied`, сборка/запуск на этом хосте недоступны до восстановления доступа к daemon; успешный CI не означает обновление сервера.
