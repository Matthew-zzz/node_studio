## Результат

На компьютере первоначальная загрузка быстрая: Lighthouse Performance 98–100. На мобильном стенде главная требует дальнейшей оптимизации: медиана 82 балла, LCP 4,36 с. При начальной загрузке Lighthouse измерил CLS 0 на всех страницах.

Сценарии взаимодействия выявили дополнительные проблемы, не видимые в коротком тесте загрузки: сдвиги при растяжении карточек услуг, задержки меню на слабом CPU и пропущенный ранний тап до готовности JavaScript на медленном 3G. Это лабораторные результаты, а не статистика всех пользователей.

### Найденные места для оптимизации

1. **Мобильное меню до завершения загрузки JavaScript.** В двух повторных проверках AnimeLove на 3G первый тап на 3,73 и 4,11 секунде не открыл меню. После завершения загрузки повторный тап работал. Точный момент готовности меню отдельно не измерялся: нельзя делать вывод, что оно не работает все 17 секунд до второго тапа. Приоритет — обеспечить доступную навигацию до hydration либо явное состояние готовности.

2. **HTTP/1.1 вместо HTTP/2.** Lighthouse и Resource Timing зафиксировали HTTP/1.1. В действующем HTTPS-блоке Nginx HTTP/2 не включён. Для мобильной главной Lighthouse оценивает потенциальное сокращение LCP примерно на 0,7–0,95 с; это модель, а не гарантированный выигрыш. Модуль HTTP/2 доступен в установленной сборке Nginx. [Конфигурация HTTP/2](https://nginx.org/en/docs/http/ngx_http_v2_module.html).

3. **Постер первого видео.** Телефон получает JPEG последнего кадра 1920 × 1080, 131 418 байт. В сценарии 4G/CPU ×6 LCP главной — 3,29 с; 2,90 с из них пришлись на загрузку ресурса постера при конкуренции с остальными запросами. В 3G/CPU ×6 LCP — 11,48 с. Пробный WebP шириной 640 px с качеством 85 занял 15 180 байт; 1280 px — 33 532 байта. Это кандидаты для последующей визуальной проверки и замены, исходник сохранён.

4. **Сдвиги при прокрутке карточек услуг.** В сценарии прохода через весь список Web Vitals зарегистрировал CLS 0,500 на обычном мобильном профиле, 0,596 на CPU ×6/4G и 0,607 на CPU ×6/3G. Источники — изменяющие высоту карточки и `.landing-service-art`. Это сдвиги во время существующего сценария открытия, отдельно от CLS 0 при начальной загрузке. Снижение CLS требует изменения способа анимации/компоновки с сохранением требуемого визуального поведения.

5. **Отзывчивость меню и карусели на слабом CPU.** В 4G/CPU ×6 наблюдался INP 232–424 мс; наиболее медленные взаимодействия — открытие/закрытие меню. Дополнительные три проверки карусели после загрузки дали 184/208/200 мс на компьютере и 152/216/216 мс на мобильном профиле CPU ×6. В компьютерном профиле значительная часть задержки — ожидание следующей отрисовки, в замедленном мобильном — ожидание и обработка событий. Для точного исправления нужен отдельный профиль этих взаимодействий, а не удаление анимаций целиком.

6. **Общий JavaScript при загрузке.** Lighthouse отмечает около 51 КБ потенциально неиспользуемого в первом экране кода в общих чанках React/Next и около 12 КБ совместимости со старыми браузерами. Оценка unused не означает, что весь этот код можно безопасно удалить: часть нужна последующим действиям. Следующий шаг — точечное уменьшение начальной клиентской работы, особенно меню и уведомлений на статических страницах.

При проходе карточек медиана межкадрового интервала составила около 16,7 мс на обычном мобильном профиле; в CPU ×6/4G — 33,4 мс, 95-й перцентиль — 66,7 мс. Это результат программной прокрутки в headless Chromium, не измерение FPS настоящего телефона.

## Ограничения проверки

- Физические iPhone и Android не подключены, сервис реальных устройств недоступен. Профили устройств задают параметры браузера и экрана; они не воспроизводят процессор, память и GPU телефона. [Описание эмуляции Playwright](https://playwright.dev/docs/emulation).
- WebKit/WPE на главной был завершён OOM-killer: в логе ядра около 1,5 ГБ RSS процесса браузера. Повторы с ограничением 650 МБ, отключённым видео, DPR 1 и скрытым оформлением не завершились; отдельный повтор карусели под лимитом 900 МБ также был прерван. Эти результаты не устанавливают причину расхода памяти и не доказывают падение Safari на iPhone.
- WebKit в этом Linux-окружении не объявляет поддержку H.264 и API LayoutShift. По нему нельзя подтвердить воспроизведение MP4 или CLS на iOS.
- Вызов публичного PageSpeed Insights API вернул HTTP 429 QUOTA_EXCEEDED. Данные реальных пользователей CrUX не получены; это не вывод об их наличии или отсутствии.
- Измерения выполнялись с VPS, где размещён сайт. Близость сервера снижает исходную сетевую задержку; ограничения сети и CPU являются искусственными. Полевой 75-й перцентиль не измерен.

Ориентиры Core Web Vitals: LCP ≤2,5 с, INP ≤200 мс, CLS ≤0,1 на 75-м перцентиле реальных посещений. Лабораторные значения из этого отчёта не дают основания объявлять сайт прошедшим все Core Web Vitals. [Официальные определения](https://web.dev/articles/vitals).

## Материалы и повторение

Численные результаты: [2026-10-30-results.json](2026-10-30-results.json). Полные 16 HTML/JSON-отчётов Lighthouse и дополнительные диагностические файлы сохранены локально в `.cache/performance-audit/2026-10-30/`.

Инструменты аудита устанавливаются отдельно от зависимостей приложения:

```bash
npm install --prefix .cache/performance-tools --no-audit --no-fund --save-exact lighthouse@13.6.0 web-vitals@6.2.3
npx playwright install chromium webkit
# Для WebKit в Linux при необходимости:
npx playwright install-deps webkit
npm run audit:lighthouse
# Chromium: обычные, замедленные и 3G-сценарии.
npm run audit:browser
# WebKit отдельно, с лимитом памяти (Linux/systemd):
sudo systemd-run --scope -p MemoryMax=900M -p MemorySwapMax=0 env AUDIT_PROFILES=iphone-webkit AUDIT_OUTPUT_DIR=.cache/performance-audit/webkit npm run audit:browser
```

`AUDIT_ORIGIN` меняет адрес сайта, `AUDIT_OUTPUT_DIR` — каталог отчётов. `AUDIT_RESUME=1` позволяет Lighthouse использовать уже сохранённые прогоны в выбранном каталоге. Для браузерного сценария доступны `AUDIT_PROFILES` и `AUDIT_ROUTES` с перечислением через запятую. После обнаруженного превышения памяти WebKit по умолчанию исключён из повторного общего запуска: он выбирается явно и запускается в отдельном каталоге с ограничением ресурсов. Не запускайте измерения параллельно с тяжёлой сборкой или другими браузерными тестами. Ошибки ограничения памяти учитывайте отдельно от ошибок продукта.

Следующие прикладные шаги: ранняя работоспособность меню на медленной сети, включение HTTP/2 и адаптивный постер главного видео. Затем — отдельная работа над метриками анимации карточек и отзывчивости меню/карусели, с повторными измерениями и проверкой Safari/Chrome на реальных телефонах.
