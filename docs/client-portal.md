# Личные кабинеты Node Studio

Рабочие кабинеты доступны на `/cabinet/`, Telegram Mini App — на `/miniapp/`. Фронтенд Next.js и сервер Node.js работают в одном Docker-приложении. Авторизация, переписка и платёжные состояния хранятся в SQLite постоянного тома; этапы, задачи и коммиты синхронизируются с GitHub.

## Роли

| Роль | Возможности |
| --- | --- |
| Клиент | Свои проекты, этапы, задачи и история коммитов; общий итоговый бриф проекта; чат, подтверждение черновиков пожеланий и оплата выставленных оценок |
| Разработчик | Весь путь клиента: Telegram-диалоги, подключение к переписке, подготовка и обновление брифа, привязка его к проекту, ссылки на оплату и выдача доступа; создание, принятие и разработка проектов, репозитории и подпроекты, этапы, задачи, оценка пожеланий |
| Администратор | Настройки ИИ, промпты, RAG и база знаний, проверка ответов, версии настроек и журнал ошибок |

Разработчик один. Он сопровождает клиента от первого обращения до сдачи работы и дальнейших изменений. Отдельного сотрудника между ними нет. Клиенты не видят чужие проекты и Telegram-переписки. Прямой доступ клиента к GitHub не выдаётся.

## От первого обращения до разработки

1. Клиент пишет [@node_studio_bot](https://t.me/node_studio_bot). ИИ объясняет, что может позвать разработчика, и помогает собрать первоначальные требования.
2. Разработчик видит очередь Telegram-диалогов. Кнопка «Подключиться к диалогу» передаёт ему управление; ИИ приостанавливает ответы. «Покинуть диалог» возвращает управление ИИ.
3. Через действия диалога разработчик запрашивает итоговый бриф. ИИ обрабатывает всю переписку по частям и собирает общее ТЗ; новая версия не уничтожает предыдущую при сбое.
4. Разработчик указывает почту, Telegram username, название проекта, ТЗ и стоимость основной работы. Подготовленная ссылка автоматически отправляется клиенту на почту и в Telegram.
5. После успешного серверного подтверждения оплаты клиент получает сообщение об успехе в оба канала. Ошибка или отмена сохраняют ожидание оплаты.
6. Разработчик запускает выдачу доступа. Существующий клиент сохраняет свой кабинет; новый получает данные для первого входа на почту. Проект создаётся без репозитория и попадает в очередь.
7. Для существующего клиента можно создать дополнительный проект без новой выдачи аккаунта: название, почта, описание и ТЗ.
8. Разработчик принимает проект и нажимает «Создать GitHub-репозиторий». Сервер создаёт закрытый репозиторий, привязывает его к этому проекту и переносит первоначальное ТЗ в первую Issue.
9. Разработчик явно выбирает проект в окне брифа. Клиент видит общий документ в обзоре и действиях чата; Telegram-переписка ему через API кабинета не раскрывается.

Создание репозитория, доставка сообщений и подготовка брифа выполняются в устойчивых очередях SQLite. Повторные запросы и перезапуски не должны создавать дополнительные проекты или репозитории. Сбои отражаются в журнале администратора вместе с инициатором и проектом.

## Пожелания и оплата

У каждого проекта свой чат. ИИ помогает сформулировать пожелание и предлагает черновик; только подтверждение клиента создаёт GitHub Issue. Разработчик сверяет её с оплаченным ТЗ. Можно включить задачу в основной объём или назначить базовую цену. Для отдельного пожелания клиентская цена включает 30% сверху; для первоначальной работы наценка не применяется.

Оценка отображается в существующем чате проекта. Клиент получает уведомление на почту и в Telegram, а после успешной оплаты — подтверждение в оба канала. Суммы хранятся целыми копейками и проверяются сервером вместе с владельцем проекта и актуальностью оценки. Менять факт оплаты вручную через интерфейс сотрудника нельзя.

До выбора платёжного провайдера используется явно обозначенная тестовая заглушка без списания денег. `PORTAL_MOCK_PAYMENTS` включает её, а `PORTAL_MOCK_PROVISIONING` отдельно разрешает выдачу доступа после тестовой оплаты. Для реального провайдера потребуется проверка серверного уведомления, подписи и суммы; возврат браузера сам по себе не доказывает оплату. [Доставка уведомлений](payment-notifications.md).

## Проекты, подпроекты и GitHub

У клиента может быть несколько проектов в одном кабинете. Очередь находится отдельно, а принятые проекты — в боковом меню разработчика. Внутри проекта доступны обзор, задачи, история и чат. На сайте два раздела можно открыть рядом. В Mini App разделы открываются по одному и помещаются в экран телефона.

Разработчик может подключить к одному клиентскому проекту несколько репозиториев, например frontend и backend. Для клиента это единый проект. Разработчик выбирает подпроект, чтобы работать с его задачами, этапами и коммитами. Один репозиторий нельзя привязать к двум проектам.

GitHub — источник состояния этапов и задач, первоначального ТЗ и полной истории коммитов. Статусы не подменяются локальными демонстрационными данными. Откат кода пока не реализован. Переписка, аккаунты, цены, платежи и связи проектов сохраняются отдельно в SQLite.

## Интерфейс и доступ

Спокойный дизайн использует цвета монограммы NS, светлую и тёмную темы, компактные действия и сворачиваемые большие тексты. Уведомления об успехе и ошибках появляются сверху. В Mini App разработчик начинает с списка Telegram-диалогов; очередь и создание проектов доступны в нижней навигации, принятые проекты — через меню.

Для входа нужны пароль и код на почту. Подтверждение действует в пределах срока cookie-сессии; после её истечения код нужен снова. Вход сопровождается письмом со ссылкой для смены пароля и завершения всех сеансов. Переключение между тремя ролями возможно только после аутентификации соответствующего аккаунта; роль и владение данными проверяются сервером.
