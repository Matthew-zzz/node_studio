# Итоговый бриф клиента

В веб-кабинете в «Диалогах» у каждого Telegram-клиента есть кнопка «Итоговый бриф». В Mini App сначала откройте диалог клиента из списка — кнопка находится внутри переписки. Она открывает сохранённое ТЗ либо ставит его подготовку в очередь, если брифа ещё нет, он завершился ошибкой или после него появилась новая переписка. Интерфейс общий для сайта и Mini App. Документ видят только кураторы. Клиенту ничего автоматически не отправляется, проект и GitHub Issue сами не создаются.

## Источник и структура

При запуске фиксируется вся сохранённая переписка одного диалога: клиент, куратор, ИИ и системные сообщения с ролями и датами. Лимит последних сообщений обычного чат-агента не применяется. Диалоги разных клиентов и чаты других проектов не объединяются. Загруженные файлы не включаются: текущий бот принимает только текст.

Для всех клиентов используются одинаковые разделы: название, цель, пользователи и сценарии, функции, дизайн и платформы, интеграции и данные, ограничения/бюджет/сроки, критерии готовности, открытые вопросы и противоречия. Шаблон и ограничения находятся в `src/features/portal/model/client-brief.ts`. Полный текст помещается в существующее поле ТЗ проекта до 16 000 символов. Куратор просматривает черновик, копирует ТЗ и использует при подготовке проекта.

ИИ должен отличать факты клиента, согласованные решения куратора и предположения ассистента. Отсутствующие сведения отмечаются как неизвестные; противоречия выносятся в вопросы. Цена, оплата, сроки и согласие не выводятся из предположений. Модель берётся из актуальных настроек Telegram-агента при запуске; системный промпт брифа отдельный, без RAG и инструментов работы с проектами. Используется Responses API с [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), `store: false`, обязательной схемой и серверной проверкой результата. Отказ, незавершённый или некорректный ответ не заменяет существующее ТЗ.

## Очередь и восстановление

`server/client-briefs.ts` сохраняет снимок в `briefRequests`, а состояние и последний успешный результат — в `clientBriefs`. Длинные сообщения разбиваются с сохранением роли, даты и номера части. Части до 24 000 символов обрабатываются полностью, затем результаты объединяются группами до получения одного документа. Ни ранние сообщения, ни хвост истории не отбрасываются.

Каждый вызов ИИ — отдельный шаг. Промежуточные результаты и следующий шаг фиксируются одной транзакцией, поэтому после перезапуска приложение продолжает с сохранённого места. Внутри существующего worker работает отдельная очередь брифов с одной одновременной генерацией: длительный запрос не блокирует обычную очередь Telegram, почты и GitHub. Дополнительного процесса или таймера нет.

При сбое выполняется до восьми попыток с увеличением задержки. Ошибка отправляется в журнал администратора с куратором и ID генерации. После остановки ручной повтор использует сохранённые промежуточные результаты, если переписка и модель не изменились. Предыдущее успешное ТЗ сохраняется при обновлении и ошибках. После завершения временный снимок удаляется.

Новые сообщения во время генерации не подменяют снимок. Интерфейс отмечает, что после брифа появилась новая переписка; её можно включить через «Обновить бриф». Повторное открытие актуального готового документа не делает новый платный вызов ИИ. «Скопировать ТЗ» копирует обычный текст; если Clipboard API недоступен, есть раскрываемое поле «ТЗ целиком» для ручного копирования.

## Проверки

`tests/client-briefs.test.mjs` проверяет роли, Origin/CSRF, всю историю, изоляцию клиентов, разбиение без потери текста, объединение, перезапуск SQLite с сохранением промежуточных результатов, независимость обычной очереди, ошибки, повтор и формат API. `tests/browser/client-briefs.mjs` проверяет кнопку, все разделы, сохранение документа, полный текст, размеры окна и нативную кнопку «Назад» в Mini App. Проверки включены в общие тесты сайта и Mini App.
