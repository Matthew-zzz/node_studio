# Запуск личных кабинетов

## Что уже работает

- `/cabinet-demo/`: четыре роли, несколько проектов, этапы, задачи, история коммитов, отдельный чат проекта, подтверждение черновика, оценка разработчика с наценкой 30%, тестовая оплата, передача диалога человеку. Поддержка получает отдельные Telegram-диалоги и создание проектов; администратор — пустой раздел.
- Демонстрация использует только браузерные сценарные данные в `nodo.portal.demo.v1`. Переключатель ролей не влияет на настоящие аккаунты. Ответы в демо не генерируются внешней моделью. Сброс демо удаляет состояние сценария, тема сохраняется отдельно.
- `server/`: вход по почте, scrypt-хеши паролей, обязательная смена временного пароля, cookie-сессии, проверка Origin и CSRF, серверные ограничения ролей и принадлежности проектов, SQLite/WAL, сохраняемая очередь внешних операций.
- Адаптер GitHub: закрытые пустые репозитории, Issues, этапы через метки, пагинация коммитов, вебхуки с HMAC и сверка API. Неподключённый GitHub не заменяется выдуманными данными.
- Адаптер Telegram: входящие текстовые сообщения, общая очередь, подключение поддержки, исходящие ответы. ИИ получает только сообщения выбранного диалога и не имеет инструментов GitHub.

Реальные ключи не настроены. Оплата исключительно тестовая. Предусмотрены необязательные адаптеры OpenAI Responses и Resend; это не выбор поставщиков за владельца студии. Другой сервис подключается через интерфейс `Integrations`, без изменений экранов и прав доступа.

## Локальная разработка

Нужен Node.js 24: сервер использует встроенные SQLite и исполнение TypeScript. Новых runtime-зависимостей нет.

```bash
npm ci
cp .env.example .env.portal
npm run portal:start
```

Во втором терминале выполните `npm run dev`. Next.js в режиме разработки автоматически передаёт `/api/portal/` на `http://127.0.0.1:3158`; Origin должен оставаться `http://localhost:3000`. Статический production-сайт использует такой же контракт через Nginx. Для проверки интерфейсов без API откройте `/cabinet-demo/`.

Аккаунты сотрудников создаются CLI. Пароль передаётся через stdin, а не аргументы командной строки. Используйте защищённый файл с правами 0600 и паролем от 12 символов, затем удалите файл. Обычная регистрация с выбором роли отсутствует.

```bash
npm run portal:user -- developer developer@example.ru "Разработчик" < /secure/password.txt
```

Для куратора используйте `curator`, для администратора — `admin`. В базе разрешён только один разработчик. Аккаунты клиентов создаются сценарием оплаченного проекта. Настоящую почту и пароль нельзя вводить в демонстрацию.

## Установка на node-studio.ru

После успешного GitHub Actions и активации новой версии сайта выполните на сервере от root из актуального checkout:

```bash
bash scripts/deploy/install-portal.sh
```

Установщик проверяет Node.js 24 и Python 3.12+, создаёт отдельного системного пользователя и службу `node-studio-portal`, добавляет Nginx proxy и генерирует секреты. Существующая TLS-конфигурация сохраняется; при неудачной проверке Nginx изменение откатывается.

Файлы:

| Путь | Назначение |
| --- | --- |
| `/etc/node-studio-portal/portal.env` | Настройки и секреты, только root |
| `/etc/node-studio-portal/bootstrap.txt` | Одноразовые доступы сотрудников, только root |
| `/var/lib/node-studio-portal/data/portal.sqlite` | Аккаунты, сессии, переписка, платежи и очередь |
| `/var/lib/node-studio-portal/releases/` | Версии API вне публичного каталога |
| `/var/lib/node-studio-portal/active.json` | Активная версия исходного кода API |

Начальные логины сотрудников: `developer@node-studio.local`, `curator@node-studio.local`, `admin@node-studio.local`. Это локальные идентификаторы входа, не адреса доставки почты. Случайные временные пароли находятся в защищённом файле; при первом входе их нужно сменить. Общедоступных тестовых паролей у настоящего API нет.

Служба читает `source_sha` из manifest уже проверенного и опубликованного сайта, получает **этот коммит**, проверяет архив и запускает его вне web root. Обновление API следует за статическим сайтом с интервалом до 30 секунд. Если новая версия API не проходит проверку запуска, служба возвращает предыдущий процесс. При обновлениях каталог данных сохраняется.

```bash
systemctl status node-studio-portal
journalctl -u node-studio-portal -n 50 --no-pager
curl https://node-studio.ru/api/portal/health
```

Установщик требует системных прав; статическая публикация через GitHub сама по себе службу не устанавливает. Скрипт supervisor устанавливается root отдельно: обновления приложения не заменяют привилегированную инфраструктуру.

## Подключения

Параметры из `.env.example` предназначены серверу. Не используйте `NEXT_PUBLIC_` для ключей. После изменения `/etc/node-studio-portal/portal.env` перезапустите службу.

**GitHub.** `PORTAL_GITHUB_TOKEN` должен принадлежать `PORTAL_GITHUB_OWNER` (по умолчанию `Matthew-zzz`) и позволять создавать приватные репозитории, читать коммиты и менять Issues. Токен пользователя из подключённого инструмента разработки не переносится в приложение. Для каждого созданного проекта настройте webhook на `https://node-studio.ru/api/portal/webhooks/github`, content type JSON, secret из `PORTAL_GITHUB_WEBHOOK_SECRET`, события Issues и Push. Если вебхука нет, открытый кабинет сверяется с API при обновлении данных (интерфейс опрашивает сервер каждые 15 секунд на активной вкладке).

Метки: `nodo:initial` — основное ТЗ, `nodo:wish` — пожелание, `nodo:stage` — этап, `nodo:in-progress` — работа, `nodo:canceled` — закрыто без реализации, `nodo:included` — входит в оплаченный объём. Закрытая Issue без отмены означает завершение. Pull requests не попадают в задачи. Тексты и статусы берутся из GitHub, первоначальное ТЗ обновляется из первой размеченной Issue. Идентификаторы в HTML-комментариях обеспечивают повтор операции после сетевого сбоя.

**Telegram.** Задайте `PORTAL_TELEGRAM_TOKEN` для `@node_studio_bot`. Вызовите официальный Bot API `setWebhook` с URL `https://node-studio.ru/api/portal/webhooks/telegram` и `secret_token` из `PORTAL_TELEGRAM_WEBHOOK_SECRET`. Токен хранится только на сервере. Входящие update ID проверяются на повтор. Принимаются личные текстовые сообщения; вложения не обрабатываются. username и технический Telegram ID сохраняются вместе с перепиской.

**ИИ.** Необязательный адаптер использует `PORTAL_OPENAI_KEY` и явно заданный `PORTAL_OPENAI_MODEL`. Модель по умолчанию не назначена. Контекст — последние 40 текстовых сообщений одного диалога; исходники, GitHub, чужие проекты и файловые вложения не передаются. Черновик создаётся отдельно от Issue. Если человек подключился во время генерации, запоздалый ответ и черновик отбрасываются. Без ключей сохраняется сообщение клиента и предлагается позвать человека.

**Почта.** Для необязательного адаптера Resend нужны `PORTAL_RESEND_KEY` и подтверждённый `PORTAL_MAIL_FROM`. У нового клиента генерируется случайный временный пароль, в базе хранится scrypt-хеш. Пока письмо ожидает доставки, его содержимое в очереди шифруется AES-256-GCM с `PORTAL_ENCRYPTION_KEY`; после доставки запись удаляется. Идемпотентность письма обеспечивается ключом отправки сервиса. Дополнительный проект привязывается к существующему клиентскому аккаунту.

**Оплата.** `PORTAL_MOCK_PAYMENTS=true` включает серверную тестовую заглушку. Она принимает результат проверки, сверяет владельца и актуальную неизменяемую оценку. Цена из браузера не принимается. Платёжная страница основной работы доступна по непредсказуемому токену во фрагменте ссылки, без авторизации до создания аккаунта. На основную работу наценки нет.

`PORTAL_MOCK_PROVISIONING=false` по умолчанию запрещает создавать реальные репозитории после тестового платежа. Для контролируемой проверки в выбранном тестовом GitHub-аккаунте этот параметр можно включить. Это всё ещё не подтверждение реальных денег. После выбора настоящего платёжного сервиса нужен отдельный адаптер с проверкой суммы, валюты, подписи и идентификатора платежа; тестовый endpoint не используется как его webhook.

## Эксплуатация и проверки

Сервер предназначен для одной реплики API на одном хосте. Перед несколькими репликами потребуется общая база и распределённая координация внешних операций. GitHub-данные в SQLite являются кэшем; аккаунты, чаты и оплаты принадлежат приложению. Банк станет источником факта реальной оплаты после интеграции.

Делайте согласованные резервные копии SQLite вместе с WAL либо через SQLite backup и сохраняйте ключ шифрования отдельно. Данные и секреты не попадают в `dist/`, GitHub или журналы. Не меняйте ключ при наличии недоставленных писем. Истёкшие сессии очищаются при входе.

Очередь повторяет неудачные операции до 8 раз с увеличением задержки; неудачное создание проекта/письмо получает статус настройки и может быть повторено поддержкой. Telegram не предоставляет ключ идемпотентности исходящего `sendMessage`: в редком случае сбоя после принятия ответа внешним сервисом возможна повторная доставка.

```bash
npm run lint
npm run typecheck
npm run build
npm test
npm run test:deploy
npm run test:e2e
```

Серверные тесты выполняются без реальных API и проверяют роли, изоляцию клиентов, пароли, CSRF, подписи вебхуков, повторные подтверждения, наценку, оплату, историю, очередь и гонку ИИ/человека. Chromium проверяет интерфейсы при 320, 390, 768 и 1440 px и настоящий вход через локальный fixture API. В изолированной среде с запретом TCP полный браузерный прогон выполняется в GitHub Actions.

Документация адаптеров: [GitHub Issues](https://docs.github.com/en/rest/issues/issues), [Telegram Bot API](https://core.telegram.org/bots/api), [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [Resend Send Email](https://resend.com/docs/api-reference/emails/send-email).
