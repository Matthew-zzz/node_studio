# Кабинеты и внешние интеграции

## Запуск

Фронтенд и API находятся в одном Docker-приложении:

```bash
docker compose up -d --build --wait
```

Вход в рабочие кабинеты — `/cabinet/`; страница оплаты конкретного заказа — `/checkout/#<token>`. Вход требует пароль и одноразовый код из письма; сессия действует 12 часов. Общая почта для нескольких ролей, уведомления и восстановление описаны в [authentication.md](authentication.md). Все данные проектов, чатов и задач поступают из API после авторизации. Роль и принадлежность проектов проверяются сервером. Публичные страницы демонстрации и локальные сценарии удалены.

Клиент видит свои проекты; разработчик использует общую очередь; разработчик — Telegram-диалоги и подготовку новых проектов. Светлая и тёмная темы доступны на экране входа, в кабинетах и оплате. Сначала учитывается системная настройка, затем сохранённый выбор пользователя, общий для вкладок. При недоступном браузерном хранилище авторизация продолжает работать через cookie, а выбранная тема сохраняется в памяти до перезагрузки.

Настоящие аккаунты, сессии, чаты и очередь хранятся в SQLite внутри постоянного тома `/data`. При первом запуске создаются разработчик и администратор. Случайные временные пароли записаны в защищённый `/data/initial-access.json`; при первом входе их нужно сменить. При пересоздании контейнера аккаунты не сбрасываются. Инструкция домена и обновления — [deployment.md](deployment.md).

Для создания дополнительного сотрудника пароль передаётся в CLI через stdin:

```bash
docker compose exec -T app node server/cli.ts create-user admin admin@example.ru "Администратор" < /secure/password.txt
```

Используйте защищённый файл с правами 0600 и паролем от 12 символов. Разработчик в системе один; клиенты создаются через оплаченный проект. Обычная регистрация с выбором роли отсутствует.

## Реализованные сценарии

Разработчик открывает «Проекты и оплаты» → «Создать проект» → «Создать для существующего клиента», указывает почту существующего клиентского аккаунта, название, описание и ТЗ. Проект сразу появляется у клиента и в общей очереди разработчика без репозитория. Для нового клиента остаётся сценарий тестовой оплаты и выдачи доступа по почте; он также создаёт проект без обращения к GitHub.

В очереди разработчик открывает окно «Изучить ТЗ проекта» и нажимает «Взять в работу». В обзоре принятого проекта доступна кнопка «Создать GitHub-репозиторий». Сервер создаёт закрытый репозиторий в настроенном аккаунте, переносит ТЗ в первую Issue и привязывает источник только к этому проекту. Повторные нажатия и повторы после потери ответа используют сохранённое имя репозитория и маркер первой Issue. До подготовки репозитория чат работает, подтверждение черновиков задач ожидает подключения GitHub; этапы, задачи и коммиты не подменяются локальными примерами.

Создание выполняется в фоновой очереди SQLite. Страница может быть закрыта, а контейнер перезапущен: незавершённая задача продолжится. Сбои автоматически повторяются до восьми попыток с увеличением задержки. Разработчик видит состояние в обзоре проекта; после остановки доступен ручной повтор с тем же именем репозитория. Повторное нажатие во время работы не создаёт вторую задачу и не сбрасывает задержку. Подробности ошибок получает администратор вместе с проектом и инициатором.

Операторская команда `node server/cli.ts archive-project` принимает JSON через stdin: `{"projectId":"project:UUID"}`. Она убирает проект из всех кабинетов и блокирует его фоновые операции, сохраняя локальную историю и GitHub-репозитории. Перед операцией сделайте резервную копию SQLite. Обычные пользователи не могут вызывать эту команду через API.

Клиент видит только свои проекты и отдельный чат каждого проекта, этапы, задачи и коммиты. ИИ готовит черновик задачи; только подтверждение клиента создаёт Issue. Разработчик видит общую очередь, сравнивает пожелание с оплаченным ТЗ, отмечает включённый объём либо выставляет свою стоимость. Итог для отдельного пожелания включает наценку 30%. Оплата отображается в существующем чате.

Разработчик может подключиться к чату и явно покинуть его. Ответы ИИ останавливаются, включая запущенную генерацию. Закрытие вкладки не освобождает диалог. Поддержка работает только с общей очередью Telegram и подготовкой проектов; задачи, этапы и чат разработки ей не выдаются. Администратор управляет ИИ-агентом Telegram: модели, промпты, функции, RAG, проверка ответов и версии настроек. Подробности — в [инструкции агента](telegram-agent.md).

Пароли защищены scrypt, сессии — HttpOnly cookie, изменения — Origin/CSRF. Фильтрация роли и владельца выполняется сервером перед отправкой данных.

Панель «Профили» внизу слева переключает настоящие аккаунты. Для каждого сначала нужны почта и пароль; на одном устройстве можно добавить до 8 аккаунтов. Сервер объединяет только подтверждённые входы этого устройства, выдаёт новый токен и CSRF при переключении и не продлевает исходные 7 дней действия профиля. Пароли и токены не помещаются в localStorage. Другие вкладки обновляются при переключении. На телефоне список открывается компактной кнопкой внизу слева. Первый вход всё так же требует смены временного пароля; существующие сессии и группы сохраняются при обновлении контейнера. «Выйти» завершает все профили этой группы; остальные устройства продолжают работать. Смена пароля отзывает остальные сессии изменённого аккаунта, включая сохранённые профили на других устройствах.

Разделы кабинета доступны только в боковом меню. На телефоне оно открывается кнопкой в верхней панели; выбор раздела закрывает меню, Escape возвращает фокус к кнопке. Путь в верхней панели остаётся в одну строку.

У клиента каждый доступный ему проект находится в боковом меню «Мои проекты» и раскрывается в разделы «Обзор проекта», «Задачи», «История» и «Чат». Эти разделы относятся к выбранному проекту; чат открывается отдельной страницей кабинета. Общие настройки остаются отдельным пунктом. Список проектов фильтруется на сервере по владельцу.

Клиент и разработчик могут нажать «Открыть рядом» и работать с любыми двумя разделами одного проекта. По умолчанию справа открывается чат; выбор раздела в боковом меню меняет левую панель и сохраняет открытый справа раздел. Разделы можно выбрать в заголовках панелей, поменять местами, развернуть на всю ширину или закрыть дополнительную панель. Черновик сообщения сохраняется при перестановке панелей и разворачивании чата. Если рядом открыты обзор и задачи, полный список задач показывается один раз. На узком экране обе панели располагаются друг под другом. Переход к другому проекту открывает отдельное рабочее пространство.

У разработчика общая очередь содержит свободные проекты. Кнопка «Взять в работу» закрепляет проект за авторизованным разработчиком на сервере и добавляет его в боковое меню «В работе». У каждого проекта раскрываются разделы «Обзор проекта», «Задачи», «История» и «Чат»; чат открывается отдельно. Выбор сохраняется между входами, устройствами и обновлениями контейнера. Запрос клиента на подключение человека остаётся виден в общей очереди: свободный проект можно взять и сразу открыть его чат. Закрепление проекта хранится как метаданные кабинета в SQLite; статусы задач и этапов, ТЗ и коммиты по-прежнему берутся из GitHub.

Ошибки и результаты действий показываются сверху через Sonner: светлая/тёмная тема, кнопка закрытия, автоматическое скрытие и объявления для скринридера. В модальных окнах уведомления находятся в том же верхнем слое, поэтому остаются видимыми и доступными. Повторяющиеся ошибки фоновой синхронизации показываются один раз до восстановления соединения или ручного повтора. Общий API — `src/lib/notifications.ts`; постоянные статусы проектов и оплаты остаются в интерфейсе.

## Настройки

Скопируйте `.env.example` в `.env`. Файл не включается в Git и Docker-сборку. После изменения настроек пересоздайте контейнер:

```bash
docker compose up -d --wait
```

Для публичного сайта внешние сервисы не обязательны. Для входа сотрудников и клиентов требуется работающая почта с кодом подтверждения. Без них реальные операции интеграций недоступны; демонстрационные записи не подставляются вместо реальных данных. Необязательные адаптеры OpenAI Responses и Resend подготовлены как варианты; поставщики пока не выбраны. Другой сервис подключается через интерфейс `Integrations`.

**GitHub.** Задайте `PORTAL_GITHUB_TOKEN` для владельца `PORTAL_GITHUB_OWNER` (по умолчанию `Matthew-zzz`). Нужны создание приватных репозиториев, чтение коммитов и изменение Issues. Ключи инструмента разработки не переносятся в приложение. Репозиторий создаётся пустым, первоначальное ТЗ становится первой Issue. Повторная операция использует тот же репозиторий и маркер Issue.

Для создания через fine-grained токен GitHub поддерживает `Repository creation: write` или `Administration: write`; классическому токену нужен `repo` — см. [документацию GitHub](https://docs.github.com/en/rest/repos/repos#create-a-repository-for-the-authenticated-user). Подключение также должно иметь доступ к новым репозиториям, `Issues: write` для задач и `Contents: read` для истории. Ошибка 403 при создании разбирается отдельно от ошибок чтения; блокировка аккаунта и ограничение частоты запросов сохраняют собственную диагностику.

Метки: `nodo:initial`, `nodo:wish`, `nodo:stage`, `nodo:in-progress`, `nodo:canceled`, `nodo:included`. Статусы и тексты задач/этапов берутся из GitHub; первоначальное ТЗ обновляется из первой размеченной Issue. Pull requests не попадают в очередь задач. История коммитов загружается постранично, включая первый коммит.

Webhook проекта: `https://node-studio.ru/api/portal/webhooks/github`, JSON, события Issues и Push; секрет `PORTAL_GITHUB_WEBHOOK_SECRET`. Если переменная не задана, первоначальный секрет находится в `/data/runtime-secrets.json`. Подпись проверяется через HMAC, доставка дедуплицируется. Открытый кабинет также сверяется с API при обновлении, интерфейс опрашивает сервер каждые 5 секунд на активной вкладке.

**Telegram.** `PORTAL_TELEGRAM_TOKEN` — токен `@node_studio_bot`. Настройте официальный Bot API `setWebhook`: URL `https://node-studio.ru/api/portal/webhooks/telegram`, `secret_token` из `PORTAL_TELEGRAM_WEBHOOK_SECRET` либо постоянного файла секретов. Поддерживаются личные текстовые сообщения; вложения не обрабатываются. username и технический Telegram ID сохраняются с перепиской. Все разработчики видят общую очередь; ответить может подключившийся сотрудник.

**ИИ.** Необязательный адаптер использует `PORTAL_OPENAI_KEY` и явно заданный `PORTAL_OPENAI_MODEL`. Модель по умолчанию не выбрана. Передаются последние 40 текстовых сообщений одного диалога. Код, GitHub, чужие проекты и вложения не передаются. Ассистент не получает инструменты работы с репозиторием. Запоздалый ответ после подключения человека отбрасывается. При отсутствии ИИ сообщение сохраняется и предлагается позвать человека.

**Почта.** Для входа и обязательного Resend-адаптера нужны `PORTAL_RESEND_KEY` и подтверждённый `PORTAL_MAIL_FROM`. Пароль нового клиента случайный, в базе хранится хеш. Ожидающее отправки письмо в очереди шифруется AES-256-GCM, после доставки удаляется. Постоянный ключ генерируется в томе; при необходимости он задаётся `PORTAL_ENCRYPTION_KEY` до первого запуска. Существующий ключ при обновлениях сохраняется. Дополнительный проект связывается с тем же клиентским аккаунтом.

**Оплата.** По текущему решению владельца на рабочем сайте используется серверная тестовая заглушка: `PORTAL_MOCK_PAYMENTS=true`. Сервер сверяет владельца и актуальную неизменяемую оценку; цена из браузера не принимается. На основную работу наценки нет, на пожелание добавляется 30% с округлением в копейках. Страница первоначальной оплаты доступна по непредсказуемому токену в ссылке до создания аккаунта. Успех, ошибка и повторная отправка проверяются сервером; результат сохраняется в SQLite и не сбрасывается после перезагрузки. При `PORTAL_MOCK_PAYMENTS=false` подтверждение отключается и интерфейс показывает недоступность оплаты. Это исключение не создаёт демонстрационные проекты и пользователей.

`PORTAL_MOCK_PROVISIONING=false` запрещает выдачу нового клиентского доступа после тестового платежа. Для проверки этого сценария параметр можно включить вместе с почтой. Создание репозитория выполняется отдельно назначенным разработчиком и требует настроенного GitHub. Настоящий платёжный сервис ещё не подключён; его подтверждение должно проверять сумму, валюту, подпись и идентификатор операции.

## Эксплуатация

Одна реплика контейнера использует SQLite/WAL и сохраняемую очередь. Для нескольких реплик потребуется общая база и распределённая координация. GitHub-данные — кэш; аккаунты, переписка и тестовые платежи принадлежат приложению.

Внешние операции повторяются до 8 раз с увеличением задержки. Неудачное создание проекта/письмо получает статус настройки и может быть повторено поддержкой. Telegram не предоставляет ключ идемпотентности для исходящих сообщений; при сбое после принятия ответа внешним сервисом возможна повторная доставка.

Проверки: `npm test`, `npm run test:e2e`, `npm run test:container`. Контейнерный тест запускает отдельный временный Compose-проект, проверяет сайт/API, настоящий вход, смену пароля и сохранность данных после пересоздания.

Документация адаптеров: [GitHub Issues](https://docs.github.com/en/rest/issues/issues), [Telegram Bot API](https://core.telegram.org/bots/api), [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses), [Resend Send Email](https://resend.com/docs/api-reference/emails/send-email).
